=> Part 5 - Amazon EBS Hands-on Lab

    -> Lab Objective

        In this lab, we will perform the complete lifecycle of an additional Amazon EBS volume with an EC2 instance.

        We will:

        -> Launch/use an EC2 instance.
        -> Create an additional EBS volume.
        -> Attach the EBS volume to EC2.
        -> Identify the attached block device in Linux.
        -> Check whether a filesystem already exists.
        -> Create an EXT4 filesystem.
        -> Create a mount point.
        -> Mount the EBS volume.
        -> Verify the mounted volume.
        -> Write and verify data.
        -> Configure persistent mounting.
        -> Unmount the volume.
        -> Detach and reattach the volume.
        -> Verify data persistence.
        -> Create an EBS snapshot.
        -> Create another EBS volume from the snapshot in another Availability Zone.
        -> Attach the restored volume to another EC2 instance.
        -> Mount and verify the restored filesystem/data.
        -> Understand and create disk partitions.
        -> Clean up all AWS resources.

        Therefore:

        VM1

    -> Step 3 - Attach the EBS Volume to VM1

        Method:

        AWS Management Console / UI

        Go to:

        EC2
          ↓
        Volumes
          ↓
        Select 5 GB Volume
          ↓
        Actions
          ↓
        Attach Volume

        Select VM1 and attach the volume.

        AWS attaches the EBS volume to the EC2 instance as a block-storage device.


    -> Step 4 - Identify the New Block Device

        Method:

        Linux CLI

        Connect to VM1 and run:

        lsblk

        Example:

        NAME         SIZE TYPE MOUNTPOINTS
        nvme0n1        8G disk
        ├─nvme0n1p1    7G part /
        ├─nvme0n1p14   4M part
        ├─nvme0n1p15 106M part /boot/efi
        └─nvme0n1p16 913M part /boot

        nvme1n1        5G disk

        Here:

        /dev/nvme0n1
        -> Existing root EBS disk.

        /dev/nvme1n1
        -> Newly attached 5 GB EBS disk.


    -> Step 5 - Check Whether the New Volume Already Has a Filesystem

        Method:

        Linux CLI

        Before formatting a volume, always check whether a filesystem already exists.

        Run:

        sudo file -s /dev/nvme1n1

        In our new volume, the output was:

        /dev/nvme1n1: data

        Also run:

        sudo blkid /dev/nvme1n1

        No filesystem information was returned.

        This indicated that the new volume did not contain a recognized filesystem.

        Important:

        Never blindly execute mkfs on an existing volume.

        If the volume already contains a filesystem and data, formatting it can destroy the existing data.


    -> Step 6 - Create an EXT4 Filesystem

        Method:

        Linux CLI

        Run:

        sudo mkfs -t ext4 /dev/nvme1n1

        This creates an EXT4 filesystem directly on the 5 GB block device.

        Verify:

        sudo blkid /dev/nvme1n1

        Our output showed:

        UUID="63935c8c-bef2-4d8a-8768-26d8db555406"
        BLOCK_SIZE="4096"
        TYPE="ext4"

        Therefore:

        5 GB EBS
            ↓
        /dev/nvme1n1
            ↓
        EXT4 Filesystem


    -> Step 7 - Create the Mount Point

        Method:

        Linux CLI

        Create a directory:

        sudo mkdir -p /data

        /data will act as the mount point for the new filesystem.


    -> Step 8 - Mount the EBS Volume

        Method:

        Linux CLI

        Run:

        sudo mount /dev/nvme1n1 /data

        Conceptually:

        /dev/nvme1n1
              ↓
            Mount
              ↓
            /data

        The filesystem on the EBS volume can now be accessed through /data.


    -> Step 9 - Verify the Mount

        Method:

        Linux CLI

        Run:

        findmnt /data

        Our output:

        TARGET  SOURCE         FSTYPE OPTIONS
        /data   /dev/nvme1n1   ext4   rw,relatime

        Here:

        /data
        -> Mount point.

        /dev/nvme1n1
        -> EBS block device.

        ext4
        -> Filesystem.

        rw
        -> Read and write access.

        Additional verification:

        df -h

        or:

        df -h /data


    -> Step 10 - Write Data to the EBS Volume

        Method:

        Linux CLI

        Create test data inside /data.

        Example:

        echo "Created on VM1" | sudo tee /data/test.txt

        Verify:

        cat /data/test.txt

        Expected:

        Created on VM1

        Anything written under /data is now stored on the additional EBS filesystem rather than the root filesystem.


    -> Step 11 - Configure Persistent Mounting

        Method:

        Linux CLI

        A manual mount does not by itself guarantee that the volume will automatically be mounted after reboot.

        First obtain the filesystem UUID:

        sudo blkid /dev/nvme1n1

        Example UUID used in our lab:

        63935c8c-bef2-4d8a-8768-26d8db555406

        Check the existing configuration:

        cat /etc/fstab

        Backup the file:

        sudo cp /etc/fstab /etc/fstab.backup

        Edit:

        sudo nano /etc/fstab

        Add:

        UUID=63935c8c-bef2-4d8a-8768-26d8db555406 /data ext4 defaults,nofail 0 2

        Save the file.


    -> Step 12 - Test the /etc/fstab Configuration

        Method:

        Linux CLI

        Reload systemd configuration:

        sudo systemctl daemon-reload

        Test all fstab entries:

        sudo mount -a

        Verify:

        findmnt /data

        To perform a stronger test:

        sudo umount /data

        Verify that it is unmounted:

        findmnt /data

        Then:

        sudo mount -a

        Verify again:

        findmnt /data

        If /data is mounted again, the /etc/fstab configuration is working.

    -> Step 14 - Unmount Before Detaching

        Method:

        Linux CLI

        Before detaching a mounted data volume, unmount its filesystem.

        Run:

        sudo umount /data

        Verify:

        findmnt /data

        If no result is returned, the filesystem is no longer mounted.

        Important:

        Unmounting does not delete the filesystem or data.

        It only disconnects the filesystem from the Linux directory tree.

    -> Step 17 - Identify the Reattached Volume

        Method:

        Linux CLI

        Run:

        lsblk

        Then verify its filesystem:

        sudo blkid /dev/nvme1n1

        Because this is an existing volume, the EXT4 filesystem should already exist.

        Important:

        Do NOT execute:

        sudo mkfs -t ext4 /dev/nvme1n1

        again.

        mkfs is used to create a new filesystem and can destroy the existing filesystem/data.


    -> Step 18 - Mount the Reattached Volume

        Method:

        Linux CLI

        If /etc/fstab is correctly configured, it can be mounted using:

        sudo mount -a

        sudo mount /dev/nvme1n1 /data

        findmnt /data

            ↓

            ↓

        Connect to VM2.

        UUID="63935c8c-bef2-4d8a-8768-26d8db555406"

        This showed that the filesystem information from the original volume was present in the restored volume.


    -> Step 25 - Do Not Format the Restored Volume

        The restored volume already contains the filesystem captured in the snapshot.

        Therefore, do NOT run mkfs on VM2.

        Incorrect:

        sudo mkfs -t ext4 /dev/nvme1n1

        Correct flow:

        Existing Restored EBS
              ↓
        Existing EXT4
              ↓
        Create Mount Point
              ↓
        Mount

        /dev/nvme1n1 on /data type ext4 (rw,relatime)

    -> Step 28 - Important Snapshot and Mount Observation

        A snapshot preserves the block-level contents of the EBS volume.

        Therefore, the restored volume can contain:

        -> Existing filesystem.
        -> Filesystem metadata.
        -> Existing files/data captured by the snapshot.

        However, mounting is an operating-system operation.

        Therefore, after attaching the restored volume to VM2, we still create/select a mount point and mount the existing filesystem.

        We do not recreate the filesystem.


    -> Step 29 - Understanding Disk vs Partition

        Method:

        Linux CLI

        Run:

        lsblk

        The root disk may appear like:

        nvme0n1
        ├─nvme0n1p1
        ├─nvme0n1p14
        ├─nvme0n1p15
        └─nvme0n1p16

        These entries are partitions.

        They are NOT the individual internal storage blocks of EBS.

        Our additional volume initially appeared as:

        nvme1n1

        without child partitions because we originally created the EXT4 filesystem directly on the whole disk.


    -> Step 30 - Create Partitions on the Additional EBS Volume

        Method:

        Linux CLI

        Important:

        Creating a new partition table on a disk that already contains a filesystem can destroy or make the existing filesystem inaccessible.

        Perform this only when the existing data is no longer required or when intentionally rebuilding the lab disk.

        First unmount the volume:

        sudo umount /data

        Start fdisk:

        sudo fdisk /dev/nvme1n1


    -> Step 31 - Create Partition 1

        Inside fdisk:

        n
        p
        Enter
        Enter
        +1G

        This creates approximately:

        /dev/nvme1n1p1
        -> 1 GiB


    -> Step 32 - Create Partition 2

        Inside fdisk:

        n
        p
        Enter
        Enter
        +1G

        This creates:

        /dev/nvme1n1p2
        -> 1 GiB


    -> Step 33 - Create Partition 3

        Inside fdisk:

        n
        p
        Enter
        Enter
        +1G

        This creates:

        /dev/nvme1n1p3
        -> 1 GiB


    -> Step 34 - Create Partition 4

        Inside fdisk:

        n
        p
        Enter
        Enter
        Enter

        For the final Last Sector, pressing Enter uses the remaining available disk space.

        This creates approximately:

        /dev/nvme1n1p4
        -> 2 GiB


    -> Step 35 - Verify the Proposed Partition Table

        Before saving changes inside fdisk, run:

        p

        Our layout was:

        /dev/nvme1n1p1    1G
        /dev/nvme1n1p2    1G
        /dev/nvme1n1p3    1G
        /dev/nvme1n1p4    2G

        Conceptually:

        /dev/nvme1n1              5 GiB
             │
             ├── p1               1 GiB
             ├── p2               1 GiB
             ├── p3               1 GiB
             └── p4               ~2 GiB


    -> Step 36 - Write the Partition Table

        After verifying the proposed partition layout, inside fdisk run:

        w

        w
        -> Writes the partition table to the disk and exits fdisk.

        Verify from Linux:

        lsblk

        Expected structure:

        nvme1n1          5G disk
        ├─nvme1n1p1      1G part
        ├─nvme1n1p2      1G part
        ├─nvme1n1p3      1G part
        └─nvme1n1p4      2G part


    -> Step 37 - Filesystems on Partitions

        After partitioning, filesystems can be created on individual partitions if they are going to be used for file storage.

        Example:

        sudo mkfs.ext4 /dev/nvme1n1p1
        sudo mkfs.ext4 /dev/nvme1n1p2
        sudo mkfs.ext4 /dev/nvme1n1p3
        sudo mkfs.ext4 /dev/nvme1n1p4

        Important:

        These commands format the partitions.

        Run them only when the partitions are intentionally being prepared as new filesystems.


    -> Step 38 - Mount Individual Partitions

        Example mount points:

        sudo mkdir -p /data1
        sudo mkdir -p /data2
        sudo mkdir -p /data3
        sudo mkdir -p /data4

        Mount:

        sudo mount /dev/nvme1n1p1 /data1
        sudo mount /dev/nvme1n1p2 /data2
        sudo mount /dev/nvme1n1p3 /data3
        sudo mount /dev/nvme1n1p4 /data4

        Verify:

        lsblk -f

        findmnt /data1
        findmnt /data2
        findmnt /data3
        findmnt /data4

        Conceptually:

        5 GB EBS
        /dev/nvme1n1
             │
             ├── p1 → EXT4 → /data1
             ├── p2 → EXT4 → /data2
             ├── p3 → EXT4 → /data3
             └── p4 → EXT4 → /data4


    -> Step 39 - Important Difference Between Blocks and Partitions

        EBS provides block storage.

        Internally, storage is handled in blocks.

        However:

        nvme1n1p1
        nvme1n1p2
        nvme1n1p3
        nvme1n1p4

        are partitions, not individual EBS blocks.

        Conceptually:

        EBS Block Storage
              ↓
        Linux Block Device
        /dev/nvme1n1
              ↓
        Partition Table
              ↓
        p1 / p2 / p3 / p4
              ↓
        Filesystems
              ↓
        Mount Points


    -> Step 40 - Resource Cleanup

        Method:

        Linux CLI + AWS Management Console / UI

        Before detaching any mounted data volumes, unmount them from Linux.

        Example:

        sudo umount /data

        or for partitioned storage:

        sudo umount /data1
        sudo umount /data2
        sudo umount /data3
        sudo umount /data4

        Then use AWS Console:

        EC2
          ↓
        Volumes
          ↓
        Detach Additional EBS Volumes

        After the volumes are detached:

        -> Delete additional EBS volumes that are no longer required.
        -> Delete snapshots that are no longer required.
        -> Terminate temporary EC2 instances.
        -> Verify that no unnecessary lab resources remain.


    -> Important Cleanup Note

        Stopping or terminating an EC2 instance does not necessarily delete every separately created EBS volume or snapshot.

        Therefore, always verify:

        EC2 Instances
        -> No unnecessary instances.

        EBS Volumes
        -> No unnecessary available volumes.

        EBS Snapshots
        -> No unnecessary snapshots.

        This avoids continuing storage charges after the lab.

    -> Final Lab Understanding

        AWS Console was used for AWS infrastructure operations such as creating EBS volumes, attaching/detaching volumes, creating snapshots, creating volumes from snapshots and managing EC2 instances.

        Linux CLI was used for operating-system-level storage operations such as identifying block devices, creating filesystems, creating mount points, mounting/unmounting filesystems, configuring /etc/fstab and creating partitions.

        The most important separation is:

        AWS Console
        -> Create and manage the EBS storage resource.
        -> Attach/detach the EBS volume.
        -> Create and restore snapshots.

        Linux CLI
        -> Detect the attached block device.
        -> Create or identify the filesystem.
        -> Mount the filesystem.
        -> Manage partitions.
        -> Access and verify stored data.

        The complete practical relationship is:

        AWS EBS Volume
              ↓
        Attach to EC2
              ↓
        Linux Block Device
              ↓
        Partition (Optional)
              ↓
        Filesystem
              ↓
        Mount Point
              ↓
        Files and Data
              ↓
        Snapshot
              ↓
        Restore New Volume
              ↓
        Attach + Mount
              ↓
        Data Available Again
