=> Amazon S3 Complete Hands-On Lab

     -> Objective

        The objective of this lab was to understand Amazon S3 practically
        by creating a private S3 bucket and performing common S3 operations.

        We also integrated Amazon EC2, IAM and S3 to understand how an
        application running on EC2 can securely access S3.

        During this lab we practiced:

        -> Creating an S3 bucket
        -> Uploading objects
        -> Object Keys and prefixes
        -> Storage Classes
        -> Metadata
        -> Default encryption
        -> Private object access
        -> S3 Versioning
        -> Version IDs
        -> Delete Markers
        -> Recovering deleted objects
        -> IAM Policies
        -> IAM Roles
        -> EC2 to S3 access
        -> Least Privilege
        -> Bucket Policies
        -> Pre-Signed URLs
        -> Complete resource cleanup

     -> Step 19 — Delete an Object with Versioning Enabled

        We turned Show versions OFF and performed a normal DELETE
        operation on the object.

        However, S3 had not deleted all previous versions.


        Instead:

        Normal DELETE
             |

             |
             v
        Delete Marker becomes Current
             |
             v

     -> Step 20 — Inspect the Delete Marker

        We enabled:

        Show versions


        We could now see:

        documents/s3.txt.txt
               |
               +-- Delete Marker
               |
               +-- Version 3
               |
               +-- Version 2
               |
               +-- null


        The Delete Marker had:

        Size = 0 B


        It did not contain the actual object data.

        It caused normal S3 requests to treat the object as deleted.


     -> Step 21 — Recover the Deleted Object

        s3.txt.txt

            |
            +-- V2

     -> Step 24 — Bucket-Level vs Object-Level ARN

        s3:GetObject

        Resource:

        arn:aws:s3:::aws-s3-learning-lab-practice/*


        Therefore:

                    S3 Permissions
                          |
               +----------+----------+
               |                     |
          Bucket Action          Object Action
               |                     |
         s3:ListBucket           s3:GetObject
               |                     |
          Bucket ARN            Bucket ARN/*
                                     |
                                  Objects

     -> Step 39 — Bucket Policy Structure

        A Bucket Policy contains fields such as:

        Version
        -> Policy language version

        Statement
        -> Permission rule

        Sid
        -> Statement ID

        Effect
        -> Allow or Deny

        Principal
        -> WHO receives permission

        Action
        -> WHAT operation is permitted

        Resource
        -> WHICH resource is affected


        Simple mental model:

                    POLICY STATEMENT
                           |
              +------------+------------+
              |            |            |
             WHO          WHAT         WHICH
              |            |            |
         Principal       Action      Resource
                           |
                         Effect
                           |
                      Allow / Deny


     -> Step 40 — Grant PutObject Using Bucket Policy

        We intentionally left the Identity-Based Policy unchanged.

        It still did NOT contain:

        s3:PutObject


        Instead, we added a Bucket Policy allowing the EC2 IAM Role
        to upload objects.


        Policy structure used:

        {
            "Version": "2012-10-17",
            "Statement": [
                {
                    "Sid": "AllowEC2RoleToUpload",
                    "Effect": "Allow",
                    "Principal": {
                        "AWS": "arn:aws:iam::<ACCOUNT-ID>:role/s3-lab-ec2-role"

                    "Resource": "arn:aws:s3:::aws-s3-learning-lab-practice/*"

            ]
        }


        Important:

        We used the IAM Role ARN:

        arn:aws:iam::<ACCOUNT-ID>:role/s3-lab-ec2-role


        We did NOT use the temporary STS assumed-role ARN.

     -> Step 49 — Pre-Signed URL vs Azure SAS URL

        The concept is similar to Azure Blob Storage SAS URLs.

        AWS:

        Private S3 Object
             |
             v
        Pre-Signed URL
             |
             v
        Temporary Access


        Azure:

        Private Blob
             |
             v
        SAS URL
             |
             v
        Temporary Access


        Therefore:

        AWS S3 Pre-Signed URL
                  ≈
        Azure Blob SAS URL


        They are conceptually similar but are different technologies
        with different implementations and terminology.

     -> Important Concepts Practically Verified

        S3 is Object Storage.

        Objects are stored inside S3 buckets.

        Every object is identified by an Object Key.

        Folder-like structures in S3 are represented using prefixes
        in Object Keys.

        S3 buckets can remain completely private while authorized
        IAM identities access them.

        Block Public Access does not prevent properly authorized
        private access.

        SSE-S3 provides server-side encryption using S3-managed keys.

        Versioning allows multiple versions of the same Object Key
        to exist.

        Objects created before Versioning is enabled can have a
        null Version ID.

        A normal delete in a versioning-enabled bucket can create
        a Delete Marker rather than deleting all previous versions.

        Removing the current Delete Marker can make the previous
        object version visible again.

        IAM Roles allow AWS workloads such as EC2 to obtain temporary
        credentials without manually storing long-term Access Keys.

        Trust Policies answer:

        "Who can assume this role?"


        Permission Policies answer:

        "What can this role do?"


        Identity-Based Policies are attached to IAM identities.

        Resource-Based Bucket Policies are attached to S3 buckets.

        Least Privilege means granting only the permissions required
        by the workload.

        We verified Least Privilege when:

        ListBucket
        -> Worked

        GetObject
        -> Worked

        PutObject
        -> Initially returned AccessDenied


        We then granted PutObject through the S3 Bucket Policy and
        verified that the same upload succeeded.

        Pre-Signed URLs provide temporary access to private S3 objects
        without making the bucket public.

        Pre-Signed URLs expire after their configured validity period.
